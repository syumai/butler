# Butler

<p align="center"><img src="docs/assets/butler-icon.png" alt="Butler icon: a brass desk bell with a deep teal push button and base on a rounded white square" width="256" /></p>

<p align="center"><em>The logo depicts a desk bell, symbolizing an assistant ready to respond when called.</em></p>

An always-listening voice AI assistant for a 32-bit ARM Android 11 (LineageOS 18.1) tablet. The UI and conversation language follow the OS locale: English by default, Japanese when the device language is Japanese.

A native Android app under development. It bundles a wake word model and only requires an OpenAI API key to be configured — a self-contained setup. On-device verification of the voice/API flow is not yet complete.

## Confirmed requirements

- Runs standalone as an Android app with no dedicated backend required; it connects to external services such as OpenAI, weather, and MCP.
- The wake word is fixed to `Hello Butler` (selection UI removed for now); `Hey Butler` was tried first but its short token sequences triggered too many false wakes, so a longer phrase was adopted. The app name is Butler, and the UI and conversation language follow the OS locale (English by default, Japanese when the device language is Japanese).
- Wake word detection is on-device only, with no fallback to cloud detection. The engine is selectable in Settings → Wake: **Julius** (a phone-loop grammar decoder run as a child process — see [third_party/julius](third_party/julius/README.md)), the default since 2026-09-16 after on-device verification, or **Vosk** (`vosk-model-small-ja-0.22`, a continuous ASR restricted to a runtime grammar), the selectable alternative. This app uses the Julius Dictation Kit. Both engines detect the Japanese pronunciation only ("ハロー、バトラー") — saying "Hello Butler" in English is not detected. Audio is sent to OpenAI only after detection or after a manual conversation start.
- Supports natural two-way voice conversation, including interruption by the user's speech while a response is playing.
- The voice conversation backend is user-selectable in Settings (Conversation → Voice API): OpenAI's **Realtime API** (`gpt-realtime` family, `/v1/realtime/calls`, the default) or the newer **GPT-Live API** (`gpt-live-1`, `/v1/live/sessions`, $0.05/min billed per second plus normal backend model/tool usage). Both connect over WebRTC. GPT-Live is a full-duplex model (it keeps listening while it speaks, where Realtime relies on turn detection) and delegates web search and Home Assistant device tools to a separate "responses" backend model (reusing the Search/backend model setting) that does reasoning and tool selection while the voice model paraphrases the result — it has no turn-complete/speech-started-stopped event, so Butler measures the silence timeout from the last transcript fragment instead. GPT-Live's remote MCP tool is not supported in this app, since its delegation only accepts `function` and hosted `web_search` tools, and its voices are English/Portuguese only (no dedicated Japanese voice — Japanese is spoken by prompt, as with Realtime's own voices in Japanese conversations). Verified on the device on 2026-09-11: a Japanese question was transcribed, delegated to the backend (hosted web search ran), answered in Japanese, and "end the conversation" went through end_conversation → `session.close` → `session.closed`; no `response.output_text.annotation.added` events arrived in that run, so the Sources list stayed empty.
- The wake state is maintained while a conversation continues. The silence timeout before ending is configurable; after a device operation the conversation ends by itself after 5 s of silence instead of waiting out the full timeout, and speaking again restores the normal silence timeout.
- No long-term memory by default; only the conversation context within the same session is retained.
- Supports web-search-based answers and can be configured for MCP integration.
- The model is given a small, non-secret device context at session start (the device's time zone, its language, and the configured weather region, if any — never API keys, tokens, or server URLs) and a `get_current_time` tool for the current local date/time/weekday, since the time changes during a session and can't be baked into that context, plus a `get_home_weather` tool for the current weather and today's/tomorrow's forecast at the configured home region, so the model uses it instead of a web search.
- Can control home appliances (lights, switches, air conditioners, etc.) directly through Home Assistant's REST service-call API via the `control_devices` tool (turn on/off, set brightness/temperature/hvac mode/volume/position and the like), without depending on Assist recognizing the phrasing or the device name; `home_assistant`'s free-text Assist command remains as a fallback for requests `control_devices` can't express. The target can be a whole room ("turn off the living room lights" operates every matching light in that area at once, and a room name can also be passed separately as `area`), every device of a kind in the home (only when the user actually said "all"/"every" one, or there's only one of that kind — otherwise Butler asks which device or room rather than silently acting on everything), or one specific device by name/id. It can also look up the current state of a device or a whole group of them (state plus key attributes such as current/target temperature, mode, or brightness) directly from Home Assistant via the `get_device_states` tool, and list the devices it knows about, including their area (via the `list_home_devices` tool and the Settings → Integrations "Home Assistant devices" row, which groups the list by room with kind/state chips) so it can tell the user what devices exist and use their exact names.
- The home screen is a swipeable four-page pager (clock, weather, smart home, music) over an image background, with a floating tab strip and page dots to navigate; the weather region is configurable. A full-screen conversation overlay (an animated orb plus live "you"/assistant captions) appears while a conversation is active — including the user's own speech, transcribed live — auto-returns to the clock after 3 minutes idle away from it, and docks into a small corner overlay when the assistant switches the page underneath (e.g. to show the weather it was just asked about) so both stay visible at once.
- A physical device is available and reachable via ADB.

## Design and validation

- [Architecture proposal](docs/architecture.md)

ADB is set up and device connectivity has been confirmed. The device is Android 11 / API 30, 32-bit ARM (armeabi-v7a), 960x480.

The build uses JDK 17 or 21, and Android SDK 35 / Build Tools 35.0.0. In this working environment, the SDK and Gradle were installed under `.tools/` (not tracked in Git).

## Setup

1. Set the Android SDK location in `sdk.dir` in `local.properties`.
2. Build with `./gradlew assembleDebug testDebugUnitTest`. The Vosk Japanese model and the Julius Dictation Kit acoustic model files are not tracked in Git; on the first build, `./gradlew` automatically runs `scripts/fetch-deps.sh`, which fetches and verifies both (Vosk from alphacephei.com, Julius's model files from the pinned dictation-kit commit on GitHub — network access is required only for the first run; the Vosk and JNA AARs themselves are resolved by Gradle from Maven Central, not fetched by this script). You can also run `scripts/fetch-deps.sh` manually. The Julius grammar (`scripts/julius-wake/wake.dfa`/`wake.dict`) is copied into the build by Gradle directly, no fetch needed; the Julius executable itself (`libjulius-bin.so`) is a separate build step (`scripts/build-julius-android.sh`/`.md`), not part of `fetch-deps.sh`.
3. Install onto the device with `adb -s SERIAL install -r app/build/outputs/apk/debug/app-debug.apk`.
4. Enter the OpenAI API key in the dedicated Settings screen. Do not write the key into source code or this README.
5. Turn on "Listen for wake phrase" (呼びかけを待つ in Japanese) and grant microphone permission.
6. Say "Hello Butler" (Japanese pronunciation "ハロー、バトラー" — English pronunciation is not detected) and, after "Please speak" is shown, start talking (in English by default, or Japanese if the device language is Japanese).

Wake word detection is entirely self-contained via the bundled Vosk model — no account, AccessKey, or runtime download is required. No Realtime connection is created while on standby, and the recording used for detection is never reused for or sent to the conversation session. WebRTC starts only after the on-device detector has released the microphone. Wake phrase detection itself works even without an OpenAI API key configured; a setup prompt is shown after detection in that case.

### Home Assistant setup

1. In Home Assistant, expose the entities you want voice control over to Assist (Settings → Voice assistants → Expose), and create a Long-Lived Access Token from your Home Assistant user profile page.
2. In the app's Settings → Integrations screen (設定 → 連携 in Japanese), enter the Home Assistant URL (e.g. `http://192.168.1.10:8123`; a fixed IP is more reliable than `homeassistant.local` on this device) and the access token, then tap "Check Home Assistant connection" to verify connectivity.
3. Once both are set, the assistant gains four tools, all resolving the target the same way — an exact entity id; an exact match on a device's full friendly name; a room/area name, optionally combined with a device kind (e.g. "living room lights"), matching every device of that kind in the area, using areas fetched separately via a cached Home Assistant template query since `/api/states` itself has no area field, or passed explicitly via the tools' own `area` parameter; a device kind alone or "all <kind>" (e.g. "lights"), matching every device of that kind in the whole home; otherwise a name-containment or, failing that, character-bigram-similarity match — ties are reported back as an `ambiguous` list of candidates rather than guessed, an area name matching nothing known returns `unknown_area` with the list of real areas, and a miss returns `not_found` with the relevant device list. For `control_devices`, resolution is additionally scope-guarded: a bare device kind with no room and no "all"/"every" word only resolves on its own when exactly one device of that kind exists in the home — otherwise (and likewise when a match would span more than one room without an "all" word) it comes back `ambiguous` instead of silently acting on every matching device, which is what let an earlier version of this feature turn off a bedroom light when asked to turn off "the living room lights" (the model had called the tool with just "lights" as the target). `control_devices` operates every device the target resolves to by calling the matching Home Assistant service on each, grouping devices that need the identical service call into one request with multiple `entity_id`s (turn_on/turn_off/toggle, set_brightness, set_temperature, set_hvac_mode, set_fan_mode, set_swing_mode, set_speed, set_humidity, open/close/stop, set_position, lock/unlock, play/pause/stop/next/previous, set_volume, mute/unmute, start/return_to_base, activate, run — see `DEVICE_ACTIONS` in `ToolClient.kt`), then returns each device's fresh state (devices the action doesn't apply to come back in a separate `skipped` list rather than failing the whole call), without depending on Assist recognizing the phrasing or the device name; `home_assistant` is a fallback that sends free-text commands through Home Assistant's Assist conversation API for requests `control_devices` can't express; `get_device_states` answers state questions for one or many devices ("what's the AC doing?", "are the living room lights on?") directly from `/api/states` and returns each device's state plus a whitelisted set of relevant attributes (it does not apply the same-room-only scope guard, since reading everything of a kind is harmless); and `list_home_devices` looks up exact device names and areas and answers "what devices do I have?"-style questions (it calls Home Assistant's `/api/states`, which lists all entities, including ones not exposed to Assist and therefore not controllable through `home_assistant`). You can check the same list yourself from Settings → Integrations → "Home Assistant devices" ("Home Assistant デバイス一覧" in Japanese), grouped by room with a kind chip and a state chip (gold when the device reads as on/active) per device, to see exactly which devices Butler can see and verify area lookup on the device itself. Every tool call is also logged (`adb logcat -s Butler`, debug builds only) with its arguments and a truncated result, to make cases like the bug above easy to trace. The Home Assistant server must be reachable over the home LAN; HTTPS with a self-signed certificate is not supported — use plain HTTP on the LAN, or a certificate trusted by the system (e.g. Let's Encrypt via Nabu Casa or a reverse proxy).

## Current features and limitations

- Kotlin / native Views. Original landscape illustration background, clock, and support for importing an arbitrary image. The illustration's colors follow the time of day (night → dawn → morning → noon → evening → night), interpolated smoothly and updated once a minute from the device's local clock; the imported photo and the weather-linked scenes are unaffected.
- A four-page home screen pager (`PagerView`, own swipe/fling/snap implementation — no AndroidX): ClockPage, WeatherPage (today/tomorrow forecast cards with condition, high/low deltas and a 6-hour precipitation table), SmartHomePage (a Home Assistant device grid with a control sheet) and MusicPage (`media_player` control), switchable by swipe or a floating tab strip. A full-screen `ConversationView` overlay (an animated `OrbView` blob plus live captions) replaces the old fixed Talk/End/Sources row, shown only while a conversation is active; it shows the user's own speech as it's transcribed (`gpt-live-transcribe` for the Realtime API, GPT-Live's own native user transcript for that backend), not just the assistant's replies. Asking about the weather mid-conversation auto-switches the pager to WeatherPage and docks the overlay into a small corner bar so both stay visible; smart-home/music refresh the same way after a device operation. Idle 3 minutes away from the clock page outside a conversation returns to it automatically.
- A dedicated, category-based settings screen (`SettingsActivity`), styled like the Android Settings app, replacing the previous settings dialog. Categories: Conversation (API key, voice API selection, models, assistant voice, silence timeout), Wake (standby toggle, wake phrase display, wake engine selection), Weather & background, Integrations (Home Assistant and MCP), and About (app info and third-party notices). Every change is saved immediately, as in Android's own Settings app.
- Wake phrase detection, engine selectable in Settings → Wake. **Julius** (default) runs a phone-loop grammar decoder as a child process over its adinnet/module protocols, with a live energy VAD segmenting the microphone stream and a confidence threshold on its word-level `CM` score — see [third_party/julius](third_party/julius/README.md) for the design and the offline comparison between the two engines. **Vosk** (selectable alternative) runs `vosk-model-small-ja-0.22` as a continuous ASR restricted to the runtime grammar `["ハロー バトラー", "[unk]"]`, with no tunable detection threshold. Both detect the Japanese pronunciation only. The phrase is fixed to "Hello Butler" (selection UI removed for now). A short synthesized chime plays once the conversation has connected and the microphone is enabled, rather than immediately on wake detection, so words spoken during the few seconds it takes to connect are not lost.
- WebRTC voice conversation, locale-aware instructions (English by default, Japanese when the device language is Japanese), semantic VAD, interruption support, a selectable output voice, and a configurable silence timeout. The voice API itself is selectable in Settings: Realtime (10 voices; marin is the default) or GPT-Live (12 voices plus marin; marin is the default there too) — the voice picker lists only the voices valid for whichever API is currently selected.
- GPT-Live limitations in this app: no remote MCP tool (its delegation only accepts `function` and hosted `web_search` tool types), Live voices cover English (Australian/British/Irish/US/Southern US/Philippine) and Brazilian Portuguese only — Japanese conversations are spoken by prompt rather than a dedicated voice — and there is no turn-complete/speech-started-stopped/output-audio-done event, so the silence timeout is measured from the last transcript fragment instead. Verified on-device on 2026-09-11 (Japanese web-search Q&A and the end_conversation flow); web-search citations were not delivered as annotation events in that run, so the Sources button had nothing to show. Debug builds log every Live event type (`adb logcat -s Butler`). Barge-in: GPT-Live decides on its own when to stop speaking (there is no client-side cancel event), and on this device it often kept talking even after the interruption had been transcribed, so when user speech is transcribed while the assistant is speaking Butler sends a `session.instructions.append` nudge ("stop now and listen", at most once per 5 s), after which the model yielded within about 2 s in on-device trials. Whether the interruption is heard at all depends on playback volume, since the device has no hardware echo canceller (WebRTC's software AEC3 is on): at media volume 4/15 interruptions were transcribed almost every time, at 7/15 only about half the time with mono playback (never with stereo, which is why output is mono now). Keep the volume moderate if barge-in matters.
- Web search via the Responses API with clickable citations, viewable from a Sources button that is shown only while a conversation is in progress. In-app history is discarded when a conversation ends, and searches specify `store: false`.
- Weather display via Open-Meteo. The region name and latitude/longitude are configurable. A place-name search UI and a persistent weather cache are not yet implemented.
- Optional weather-linked home screen background ("Change background with the weather" in Settings): when enabled, the background is replaced by a code-drawn scene matching the current outdoor weather code and day/night state (clear, partly cloudy, cloudy, fog, rain, snow, thunder), redrawn on each 15-minute weather refresh. Off by default; when off, or while the scene is unknown, the imported photo or the original illustration is shown as before.
- The weather background animates: rain and snow fall (rain in three depth layers, nearly vertical with a slight, consistent wind lean), clouds and fog drift slowly, night stars twinkle, and thunder scenes flash periodically. Animation is capped at ~25 fps and only runs while the app is visible; the static clear-day scene and the imported photo/illustration paths are unaffected. See [Architecture](docs/architecture.md) for how the render cost is kept low on the target device.
- One public HTTPS MCP server can be configured, with on-screen approval for each call. LAN-based MCP clients, OAuth flows, and managing multiple servers are not yet implemented.
- Home Assistant integration is a set of client-side function tools that talk to a LAN Home Assistant server directly (a Long-Lived Access Token, not the MCP server integration, so nothing needs to be exposed publicly): `control_devices` resolves the target — which may be a whole room, every device of a kind, or one specific device — and calls Home Assistant's `/api/services/<domain>/<service>` REST endpoint directly (a fixed, whitelisted action-to-service mapping per entity domain), grouping several targeted devices that need the same call into a single request; `get_device_states` answers state questions for one or many devices by reading `/api/states` and resolving the target the same way; and `home_assistant` is now a fallback to the `/api/conversation/process` Assist endpoint for the rare request that doesn't fit `control_devices`'s action set — so both operating and querying devices no longer depend on Assist recognizing the phrasing, the device's name, or the room name for the common cases. Areas (rooms) are fetched separately, since `/api/states` carries no area field, via a Jinja template posted to Home Assistant's `/api/template` endpoint that pairs every `entity_id` with `area_name(entity_id)`; the result is cached for 10 minutes, and any failure to fetch it degrades gracefully to name-only matching rather than breaking the tools. Cleartext HTTP is allowed for this LAN traffic; HTTPS with a self-signed certificate is not supported. Unlike the MCP tool, there is no per-call on-screen approval — the model is instructed to confirm risky actions (unlocking, high-cost or dangerous operations) verbally before calling `control_devices` or `home_assistant` for them.
- A smart-home page shows every Home Assistant device (lights, switches, climate, covers, fans, locks, media players, humidifiers, vacuums, scenes, scripts) as a tile in a 4-column grid, grouped by area; tapping one opens a bottom sheet with domain-specific controls — a round dial with mode/fan/swing chips for climate, brightness/color-temperature sliders and scene chips for lights, toggles, position/speed/humidity sliders, and simple action chips for covers/fans/humidifiers/locks/media players/vacuums/scenes/scripts — that call the same Home Assistant service-call API as the voice tools, with the grid refreshing automatically after the assistant itself operates a device.
- A music page shows the selected Home Assistant `media_player`'s artwork, title/artist/album, a live progress bar, and transport/volume/mute controls, with chips to switch players when more than one exists. This is best effort: it depends entirely on Home Assistant's `media_player` integration for whatever is actually playing — there is no direct Spotify SDK or Android notification-listener integration, so anything Home Assistant doesn't expose as a `media_player` entity won't show up here.
- The API key is encrypted with Android Keystore, and backups are disabled. This does not guarantee full key protection if the device itself is compromised.
- Targets a specific Android 11 device (targetSdk 35, armeabi-v7a). Not configured for Play Store publication.
- Registers as a HOME app candidate but does not automatically change the default HOME app. Recovery after reboot, long-duration standby, and real voice quality all still require on-device validation.

Loading the model takes several seconds the first time detection starts (about 6-10s on the device — Vosk additionally unpacks its ~99MB model from assets to internal storage once, on the very first use only, then loads it). While the service is running, the weights are reused, and only the audio stream/recognizer is discarded and recreated for each conversation.

The wake word can be verified without an API key. Voice conversation with OpenAI is verified after registering an API key. The default model ID is configurable in Settings and depends on availability per account.

## Wake word on-device testing

After `./gradlew assembleDebug assembleDebugAndroidTest`, install both APKs onto the same device.

```sh
adb -s SERIAL install -r app/build/outputs/apk/debug/app-debug.apk
adb -s SERIAL install -r app/build/outputs/apk/androidTest/debug/app-debug-androidTest.apk
adb -s SERIAL shell am instrument -w dev.syumai.butler.test/dev.syumai.butler.WakeInstrumentation
```

`PASS` indicates success. `-e mode record -e seconds N` records N seconds of real microphone audio to the app's external files directory for offline analysis of how the model hears a speaker (used to tune the wake phrase's grammar for Japanese pronunciation). This runner is not a normal JUnit runner; it runs via `am instrument`. It feeds the same fixtures to both bundled wake engines in turn: the actual bundled Vosk model, 16kHz PCM audio for the wake phrase, other sentences, and silence: two fixtures of the Japanese pronunciation of "Hello Butler" (`hello-butler-ja.pcm`, `hello-butler-ja-2.pcm`, two different TTS voices), three negative fixtures (`ordinary-speech.pcm`, English; `ordinary-speech-ja.pcm`, a neutral Japanese sentence; and `near-miss-ja.pcm`, a short Japanese phrase chosen because the model hears a bare "バトラー" in it), and the two English-pronunciation fixtures (`hello-butler.pcm`, `hey-butler.pcm`) fed through but not asserted either way, since neither engine detects English pronunciation — printing the Vosk model load/unpack time. It then runs the same fixtures against Julius, spawning the real `libjulius-bin.so` child process and feeding it 100ms silence chunks for up to 4s after each fixture (since Julius's results arrive asynchronously after its VAD closes the segment), reporting `Julius: PASS/FAIL` separately and its process-startup and model-unpack times; the overall result is FAIL if either engine fails. Julius's negative fixtures are hard-asserted (must stay silent, verified true); its two positive (OpenAI-TTS) fixtures are fed through and reported (`N/2 positive fixtures hit`) but not hard-asserted, since this JNAS acoustic model — validated only against one real speaker's recordings — was confirmed (by replaying the exact adinnet bytes through `scripts/julius-adinnet-client.py`, bypassing the Kotlin client, across several penalty settings) to decode both synthetic fixtures entirely as `<garbage>` with the wake word never even proposed as a candidate, matching the already-documented "0/5 on synthetic TTS voice" finding in [third_party/julius](third_party/julius/README.md). The fixtures are synthetic audio generated with the OpenAI TTS API via `scripts/generate-fixtures.py` (see `app/src/androidTest/assets/FIXTURES.md` for the model, voice, and text used for each one), and this does not substitute for validating pronunciation accuracy with a microphone, at a distance, or with Japanese speakers. `scripts/vosk-eval.py` (run with `.tools/vosk-python/bin/python`, a venv with `pip install vosk`) evaluates the Vosk engine's grammar/adjacency-rule detection against arbitrary `.pcm` recordings offline, printing per-file final/partial hit counts and decode time — the same recording flow (`-e mode record`) captured for offline tuning; `scripts/julius-eval.py` is the Julius counterpart (see [third_party/julius](third_party/julius/README.md) for the 2026-09-15 offline comparison between the two engines). The end-to-end workflow (recording, evaluation, grammar/adjacency-rule tuning, on-device validation) is documented as the `.claude/skills/wake-tuning/SKILL.md` Claude Code skill.

The provenance, license, and hashes of the distributed Vosk artifacts are documented in [third_party/vosk](third_party/vosk/README.md); the same for Julius and the Julius Dictation Kit acoustic model is in [third_party/julius](third_party/julius/README.md). Neither model is included in Git; `scripts/fetch-deps.sh` fetches and verifies both (the Vosk and JNA AARs are resolved by Gradle from Maven Central; the Julius grammar is copied from `scripts/julius-wake/` by Gradle, and the Julius executable is a separate build step, `scripts/build-julius-android.sh`/`.md`).
