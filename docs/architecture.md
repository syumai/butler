# Architecture proposal

The following is a design proposal made before implementation. Confirmed user requirements are documented in the README.

## Standalone Android configuration

Built as a native Kotlin app, separating the home screen, a foreground service handling the microphone, conversation state management, voice communication, tool execution, and settings storage.

Voice conversation uses a WebRTC connection, over one of two user-selectable backends (`Settings.voiceApi`, default Realtime): the OpenAI Realtime API (`/v1/realtime/calls`) or the newer GPT-Live API (`gpt-live-1`, `/v1/live/sessions`). Both model IDs are configurable; availability and Japanese-language quality will be verified with a real account before deciding on defaults. `WebRtcClient` (`app/src/main/java/dev/syumai/butler/WebRtcClient.kt`) owns all native WebRTC lifecycle (peer connection, audio device module, data channel, ICE) and is backend-agnostic; a small `Signaling` interface (`request(sdp): Request`, `answer(body): String`) supplies the one thing that differs — the HTTP call that exchanges the local SDP offer for a remote answer, and the session configuration sent with it. `RealtimeSignaling` builds the existing multipart `/v1/realtime/calls` body (session `instructions`/`audio.output.voice`/`audio.input.turn_detection`, plus the `tools` array passed in from `AssistantService.begin()` — see "Latency" below; the answer is the raw response body); `LiveSignaling` builds the JSON `/v1/live/sessions` body (`{"session": {model, instructions, audio.output.voice, delegation: {type: "responses", responses: {model, instructions, tools, tool_choice, parallel_tool_calls}}}, "transport": {type: "webrtc", sdp}}`, with the delegation `tools` coming from `ToolRegistry.liveDefinitions()`) and parses `transport.sdp` out of the JSON response (`answer()` is wrapped in `runCatching` by `WebRtcClient`, failing the connection on a parse error). Per GPT-Live's docs, the offer is posted only once ICE gathering completes (or a 1500ms fallback elapses, since no ICE servers are configured and gathering is normally fast) rather than immediately after `setLocalDescription`, which `WebRtcClient.connect()` waits for on both backends (see "Latency" below for the `prepare()`/`connect()` split).

**Latency**: an on-device timeline measured 2026-09-17 found ~1.58s from `WebRtcClient.start()` to the session being ready, split roughly into peer-connection setup (~100ms), ICE gathering (~270ms), the signaling POST (~440ms, dominated by a fresh DNS+TCP+TLS handshake since a new `OkHttpClient` was built and evicted every conversation), the ICE/DTLS/SCTP handshake (~670ms, network-bound, left alone), and the `session.created`→`session.update`→`session.updated` round trip (~100ms). Three changes (and one experiment that was reverted) address the parts that don't need to be on the network's critical path:
- **Shared, pre-warmed HTTP client**: `SignalingHttp` (`WebRtcClient.kt`) is one process-wide `OkHttpClient` with a 10-minute `ConnectionPool` keep-alive, replacing the old per-`WebRtcClient` client that was built and evicted every conversation; `WebRtcClient.close()` now only cancels its own in-flight call, so the pooled TLS/h2 connection survives between conversations. `SignalingHttp.warm()` fires a throttled (`WarmThrottle.shouldWarm`, once per 60s, unit-tested in `WarmThrottleTest` since it takes `now`/`lastAt` as parameters rather than reading the clock itself), fire-and-forget, unauthenticated `HEAD /v1/models` purely to prime that pooled connection ahead of the real signaling POST — called both when the wake engine reports ready (standby begins) and on speech onset during standby (see the wake-word section's `WakeDecoder.onSpeechStart` below). Debug builds attach an OkHttp `EventListener` to log connection-reuse timing (tag `Butler`, prefix `latency:`) so `adb logcat` can confirm the signaling POST reused the warm connection.
- **Tools still go in a follow-up `session.update`** (tried and reverted): sending `registry.definitions()` with the initial `/v1/realtime/calls` config so that `session.created` could be the ready event was tried on 2026-09-17 — the endpoint accepts it (the echoed `session.tools` count matched), but on device `session.created` then arrived ~320ms after the data channel opened instead of ~2ms, i.e. ~200ms *later* than the `session.created`→`session.update`→`session.updated` round trip it was meant to remove. So `AssistantService` keeps sending tools in `session.update` on `session.created` and treats `session.updated` as ready.
- **Pre-built WebRTC peer connection during standby**: `WebRtcClient` is split into `prepare()` (peer connection factory/ADM/data channel/offer + ICE gathering — no network I/O, no audio focus, no `audio.mode`/speakerphone change) and `connect(signaling, event, failure, milestone)` (audio focus + posting the offer once ICE gathering completes). `AssistantService` builds and `prepare()`s a `prepared: WebRtcClient?` on the main thread right after the wake engine's `ready` callback (so it doesn't compete with Julius startup), and `begin()` consumes it (falling back to building+preparing inline if it's missing, stale (30+ minutes old), or was marked broken by a pre-`connect()` SDP/ICE failure via an `onBroken` callback) so the ICE-gathering leg is already done by the time a conversation starts. A `ConnectivityManager.NetworkCallback` rebuilds the prepared client (throttled to ~2s) on network changes, since its already-gathered host ICE candidates would otherwise point at addresses on a network that's no longer current.
- **Debug timing log**: debug builds log one `latency:`-prefixed line per connect-timeline milestone (begin, connect() called, HTTP response, ICE connected, data channel open, `session.created`, ready/chime), with ms elapsed since the wake engine's `detected()` callback (or since `begin()` itself for the TALK path) — `adb logcat -s Butler | grep latency:` gives the full breakdown.

Instead of the usual backend-mediated authentication setup, the app accepts the user's own API key in its settings and connects to the API directly from the device. The key is not embedded in the APK. Credentials are encrypted with an Android Keystore key and excluded from backups and logs. This approach does not guarantee key protection if the device itself is compromised. This is a design decision driven by the standalone operation requirement, and differs from OpenAI's recommended backend-based configuration.

## Voice and state management

The base states are `Stopped / Waiting / Connecting / Listening / Responding / ExecutingTool / AwaitingApproval / Recovering`. Because voice I/O and tools can overlap, speech, playback, response, and running tools are tracked separately from the state display.

1. Once the user grants permission and starts the app, a microphone foreground service monitors for the wake word.
2. Upon detecting the selected wake phrase, the connection process begins. The microphone is handed off carefully so the wake word detector and WebRTC recording do not contend for it.
3. Connection completion is indicated visually and with a short sound, and the conversation proceeds in Japanese. Any speech dropped during connection and the buffering approach for leading audio will be validated on the device.
4. The end-of-conversation timer is cleared when speech begins. The conversation is not ended midway through an AI response or tool processing.
5. The silence timer starts only after response audio playback finishes. The generation-finished event and playback-finished event are treated separately.
6. On timeout, an end button press, or an end-of-conversation utterance, the connection is closed, audio/history/tool results are discarded, and the app returns to wake word monitoring.
7. On disconnection, retries are limited. Audio or tool results from a stale session must not leak into a new session.

On user interruption, playback stops and the server-side response cancellation and conversation context are synchronized. Whether the app reacts to its own speaker output, the effectiveness of AEC, and the audio input source will all be verified on the actual device.

Separate from the conversation-end timer, there are upper time limits on connection and tool execution. An approval-pending state has a cancel option and an expiry, and execution never proceeds without approval.

On Android 11, a foreground service started from the background has microphone-usage restrictions. After reboot, the app is a candidate to launch as the default HOME app, and the service is started from a visible Activity. BOOT_COMPLETED alone does not guarantee continuous recording, and automatic recovery from a force-stop is not guaranteed either.

## Wake word

Picovoice was rejected because its registration requirements do not fit. sherpa-onnx (a lightweight ONNX keyword spotter) was used from 2026-09-06 to 2026-09-11, then removed in favor of Vosk after a real-recording evaluation. Wake detection is on-device only, behind a `WakeDecoder` interface (`accept(samples: ShortArray, count: Int): Boolean`, `restart()`, `discardAudio()`, `onSpeechStart: (() -> Unit)?`, `AutoCloseable`) — samples are passed through from the microphone buffer as raw 16-bit PCM, converted as each implementation needs. `JuliusWakeDecoder` (default) and `VoskWakeDecoder` (selectable alternative) are the two implementations, selected by `Settings.wakeEngine` (`WakeEngine.VOSK`/`WakeEngine.JULIUS`, Settings → Wake → Wake engine); the interface documents the contract and keeps `WakeModelStore`/`LocalWakeWordEngine` decoupled from either one. `WakeModelStore.acquire(context, phrase, engine)` builds and caches the decoder, keyed on both the phrase and the engine — a change to either rebuilds it. Both decoders unpack their asset tree from `assets/` to `filesDir` via the shared `AssetUnpacker` (temp-dir-then-rename, `.ready` marker), previously duplicated inline in `VoskWakeDecoder`.

`onSpeechStart` is a speculative-latency hook, not part of wake detection itself: `JuliusWakeDecoder` wires it to its `WakeVad`'s existing `onSegmentStart` callback, so it fires as soon as a segment of speech begins — well before the phrase is confirmed — and `LocalWakeWordEngine` (which takes a new `speech: () -> Unit` constructor callback, delivered on the main thread like `ready`/`detected`/`failed`, and cleared in its `finally` block) forwards it to `AssistantService`, which calls `SignalingHttp.warm()` from it. `VoskWakeDecoder` has no VAD/segment concept (continuous ASR) so its implementation stores the listener but never invokes it. This only ever fires during standby, and the callback itself must stay cheap since it runs on the wake worker thread.

**`VoskWakeDecoder`**: Vosk 0.3.75 (`com.alphacephei:vosk-android`, depends on JNA for its native bridge) running `vosk-model-small-ja-0.22` as a continuous small-vocabulary ASR restricted, via `Recognizer`'s runtime grammar parameter, to exactly `["ハロー バトラー", "ヘイ バトラー", "[unk]"]` — free-vocabulary decoding was measured to be both slower (3.8s vs 0.4s to decode 60s of audio on a desktop CPU) and less accurate (9/11 vs 11/11 spoken utterances detected) than grammar-restricted decoding, so grammar mode is what ships. `WakePhrase` has a single member, `HELLO_BUTLER`, whose `voskPhrases` (`listOf("ハロー バトラー", "ヘイ バトラー")`) are both fed into the grammar and checked — Japanese pronunciation only, since the model is a Japanese acoustic/language model and does not reliably recognize the English pronunciation. `accept()` calls `Recognizer.acceptWaveForm` and, only once it returns `true` (a final result), inspects `getResult()` (JSON) via `voskPhrases.any { VoskWake.hit(json, it) }` — `VoskWake.hit` (pure Kotlin, unit-tested in `VoskWakeTest.kt`) requires one phrase's words to appear as a contiguous run in the whitespace-split recognized token list, not merely both present somewhere; a real negative recording showed the model transiently surfacing a bare `ハロー` or a bare `バトラー` in its partial results even in grammar mode, so the weaker "both words present" check would false-wake. Partial results (`getPartialResult()`) are not checked at all: an offline eval on 2026-09-15 against ~92 minutes of unrelated Japanese speech found 25 false wakes, all at the partial-result stage and none at the final-result stage, so `accept()` only reacts to final results, at the cost of roughly 1s more latency. The unpacked model (~99MB, including the runtime-grammar-capable `HCLr.fst`/`Gr.fst`) ships as gitignored assets under `assets/vosk/vosk-model-small-ja-0.22/`, fetched and verified by `scripts/fetch-deps.sh` (see [third_party/vosk](../third_party/vosk/README.md)); at runtime `VoskWakeDecoder` unpacks it once to `File(context.filesDir, "vosk/vosk-model-small-ja-0.22")` on first use via `AssetUnpacker` (`Model`'s constructor needs a real filesystem path) — `org.vosk.android.StorageService` is not used, since it expects a `uuid` asset and the external files dir, neither of which fits this app's bundling. Because it runs continuous ASR rather than a lightweight keyword spotter, Vosk is heavier on CPU/RAM while listening than the previous engine. There is no confidence threshold to tune — the grammar restriction plus the word-adjacency rule are the only detection knobs.

**`JuliusWakeDecoder`** (default since 2026-09-16, after on-device verification): runs the bundled `libjulius-bin.so` (Julius 4.6 cross-compiled to armeabi-v7a, see [third_party/julius](../third_party/julius/README.md) for the build and the 2026-09-15 offline comparison against Vosk) as a child process rather than via JNI, since Android 10+'s W^X policy only allows executing files from `nativeLibraryDir` — `app/build.gradle.kts`'s `packaging.jniLibs.useLegacyPackaging = true` makes the system extract the "library" there at install time so it can be `exec`'d, and `copyJuliusGrammar` copies `scripts/julius-wake/wake.dfa`/`wake.dict` into a generated assets dir (that directory stays the single source of truth for the grammar; nothing is committed under `app/src/main/assets/`) while `scripts/fetch-deps.sh` fetches the two acoustic-model files into `assets/julius/model/`. `JuliusWakeDecoder` starts it with `-input adinnet -module <port>`, connecting a module-protocol client first (Julius blocks on that before opening its adinnet server) and then an adinnet-protocol client, both loopback TCP, each retried for up to 15s; both stdout/stderr are drained by rate-limited logging threads. Since Julius does not cut silence for adinnet input (`-nocutsilence`), `WakeVad` — a pure-Kotlin port of `scripts/julius-eval.py`'s offline energy VAD (10ms frames, RMS threshold, ~300ms hangover, 200ms ring-buffered pre-roll, 8s force-end; unit-tested in `WakeVadTest`, including against the real `.tools/hello-butler-ja-rec1.pcm` fixture when present) — decides segment boundaries live, streaming each segment to the adinnet socket as 4-byte-little-endian-length-prefixed s16le packets terminated by a 0-count packet; a background thread reads and discards the single command bytes (`'0'`/`'1'`) Julius writes back on that socket. Recognition results are read line-by-line from the module socket (XML fragments, `<RECOGOUT>`/`<SHYPO>`/`<WHYPO WORD="..." CM="..." .../>`, terminated by a lone `.` line) and fed to a `JuliusWake.BlockParser` — a pure-Kotlin, unit-tested (`JuliusWakeTest`) accumulator that judges a whole `<RECOGOUT>` block at once rather than any single `<WHYPO>` line: a hit requires a `WHYPO` whose `WORD` equals any entry of the wake phrase's `juliusWords` (`listOf("ハローバトラー", "ヘイバトラー")` since 2026-09-17 — see [third_party/julius](../third_party/julius/README.md)'s "Hey Butler" section) with `CM` (Julius's confidence measure) parsing as a number >= 0.05 (missing/`CM="-"` counts as not confident) AND at most 10 total `<garbage>` `WHYPO` words in that same block — the second gate exists because `CM` alone doesn't separate ヘイバトラー's genuine hits from its false wakes (their ranges overlap), but the surrounding filler-word count does: false wakes sit inside long runs of speech with many fillers, genuine hits are short standalone segments with few. A hit sets an `AtomicBoolean` that `accept()` polls and clears; `restart()`/`discardAudio()` reset the VAD (ending any open segment with its terminator packet) and clear the flag; `accept()` throws if the process has died or a socket has failed, which `LocalWakeWordEngine` maps to `failed()` like any other decoder exception.

`LocalWakeWordEngine` performs 16kHz microphone capture and inference on a dedicated thread, and on stop it releases the microphone and audio stream before invoking the callback. Only the model weights are kept and reused within the service, and released when the service ends. The service starts WebRTC only after that release completes. Audio used for detection is neither retained nor sent. There is no fallback to cloud detection or an authentication server.

`WakeChime` plays a short synthesized chime, but not on detection itself: `AssistantService` defers it until the following conversation's `session.updated` event reports the session ready, right after `enableMicrophone()`. Playing it earlier, on the `detected` callback, let users start talking during the several seconds the WebRTC connection takes to come up, and that speech was lost because the microphone was not yet enabled.

The old Picovoice key and custom model are removed when settings are reset.

## Tools and MCP

Executable tools live in `dev.syumai.butler.tools`: a `Tool` interface (`name`, `busyStatus`, `definition()`, `execute()`) plus one class per tool (`GetCurrentTimeTool`, `SearchWebTool`, `HomeAssistantTool`, `ListHomeDevicesTool`, `GetDeviceStatesTool`, `ControlDevicesTool`), each wrapping `ToolClient` (except `GetCurrentTimeTool`, which needs only a `Context` for its localized strings). `ToolRegistry` builds the available tool list from `Settings` (`GetCurrentTimeTool` and `SearchWebTool` are always included; `HomeAssistantTool`, `ListHomeDevicesTool`, `GetDeviceStatesTool` and `ControlDevicesTool` only when both the Home Assistant URL and token are set), dispatches a function call by name (`find`), and assembles two different tool arrays: `definitions()` for the Realtime `tools` array — the executable tools, then `end_conversation` (kept as a plain JSON constant on the registry rather than a `Tool`, since it is conversation control flow with nothing to execute), then the optional hosted MCP tool — and `liveDefinitions()` for GPT-Live's delegation `tools` array — every executable tool including `SearchWebTool` (see "Search cards" below for why Live no longer uses the hosted `web_search` tool type here), then `end_conversation`; no MCP entry, since Live delegation only accepts `function`/`web_search` tool types. Adding a tool means adding a class here and listing it in `ToolRegistry`; `AssistantService` itself never changes.

`GetCurrentTimeTool` (`GetCurrentTimeToolTest`) exists because the current date/time is deliberately *not* baked into the static session instructions below — it changes during a session — so the model is instead instructed to call this tool whenever an answer depends on it. Its pure, unit-tested `payload(epochMs, zone, locale)` builds `{"datetime" (ISO-8601 with offset), "date", "time", "weekday" (localized full name), "time_zone", "utc_offset", "epoch_seconds"}` from `java.text.SimpleDateFormat` pinned to the given `TimeZone`/`Locale`; `execute()` just calls it with the real clock/zone/locale. `AssistantService.runToolAsync` treats a blank `arguments` string (some models send `""` rather than `"{}"` for a no-argument call) the same as `"{}"`.

`get_home_weather` (`GetHomeWeatherTool`, always registered — unlike the Home Assistant tools, it doesn't require any configuration to be listed, only to succeed) answers weather questions ("what's the weather at home", "will it rain today/tomorrow", "do I need an umbrella") without a web search. `Forecast.parse` (`Forecast.kt`, `ForecastTest`) is a pure-Kotlin (`org.json` only) reduction of `ToolClient.forecast(lat, lon)`'s Open-Meteo response — `current`/`hourly`/`daily` with `past_days=1&forecast_days=2&timezone=auto` — into a `Forecast(currentTemp, currentCode, isDay, currentTime, days)`, where `days` is today and tomorrow (today is the `daily` entry whose date matches `current.time`'s date, falling back to daily index 1 if that ever fails to line up). Each `DayForecast` carries the daily high/low, their rounded change versus the previous day (`null` when that day is missing), a 4-element `precipitation` array (max hourly `precipitation_probability` per 6-hour block, `-1` for no data), and `codeFirstHalf`/`codeSecondHalf` — one representative WMO code for the dominant `WeatherScene` category among that half-day's hourly rows (ties broken by severity: thunder > snow > rain > fog > cloudy > partly cloudy > clear), falling back to the daily code when no hourly rows matched the date. `WeatherStore` is a small in-memory cache (`current(client, lat, lon, now, maxAgeMs = 15min)`) shared by the tool and (once built) the home screen, so both read one fetch instead of hitting Open-Meteo independently; it takes `now` as a parameter rather than reading the clock itself, keeping it pure and unit-testable. `WeatherFormat` (`WeatherFormatTest`) holds the small pure display helpers built on top — `emoji`/`labelRes` per `WeatherScene` (the latter reusing the existing `weather_sky_*` strings), `conditionParts` (a day's first-half scene, plus its second-half scene only when the category differs), and `deltaText`/`precipitationText` for rendering `[+2]`/`[-4]`/`[0]` and `60%`/`–`. `GetHomeWeatherTool`'s own JSON assembly is a pure, unit-tested `payload(forecast, place, conditionText, currentConditionText)` (`GetHomeWeatherToolTest`) — `execute()` just supplies the localized condition strings and reports `{"error": "region_not_configured"}` when `latitude`/`longitude` aren't set in `Settings`, or `{"error": "fetch_failed"}` when the Open-Meteo call itself fails.

`SessionContext` (`dev.syumai.butler/SessionContext.kt`, `SessionContextTest`) builds the small, non-secret context paragraph appended to the session instructions on both signaling paths below: the device's time zone id and UTC offset, its display language, and — only when configured — the weather region's name and/or coordinates from `Settings` (`location`/`latitude`/`longitude`), plus a fixed sentence pointing the model at `get_current_time` for anything date/time-related. Its pure `facts(location, latitude, longitude, zone, locale, now)` (taking the raw `Settings` values rather than `Settings` itself, so it needs no Android `Context`) computes the localized language name and the `+HH:MM`/`-HH:MM` offset string (shared with `GetCurrentTimeTool` via `SessionContext.formatUtcOffset`); `text(context, settings)` turns those facts into the localized paragraph, omitting the region sentence entirely when there's neither a name nor a full lat/lon pair, and filling a missing name or coordinate with an "unnamed"/"unknown" placeholder rather than dropping the sentence. Nothing secret (API keys, tokens, the Home Assistant URL, the MCP URL) is ever included.

`AssistantService` keeps only Android/side-effecting code: sending Realtime/Live JSON, the foreground-service and wake-word lifecycle, threads, and status text. It picks a backend per conversation in `begin()` from `settings.voiceApi` (`RealtimeSignaling`/`ConversationState`/`onEvent` vs. `LiveSignaling`/`LiveConversationState`/`onLiveEvent`, tracked by a `live: Boolean` field), both wrapping the same `WebRtcClient`. For Realtime, the per-conversation flags — readiness, speech/response/playback in flight, pending tool calls, whether a follow-up `response.create` is due, the `end_conversation` flow, MCP call/approval bookkeeping, and the call-count limit — live in `ConversationState`, a pure Kotlin class (no Android imports, same spirit as `IdlePolicy`, unit-tested in `ConversationStateTest`) with one method per Realtime event (`sessionReady`, `speechStarted`/`speechStopped`, `responseCreated`, `audioStarted`/`audioStopped`, `callStarted`, `toolCallStarted`/`toolCallFinished`, `endRequested`, `mcpCallStarted`/`mcpCallFinished`/`mcpCallFailed`, `responseDone`) plus `busy` and `shouldFollowup`/`tryFollowup`. `AssistantService` creates a fresh `ConversationState` in `begin()` and reacts to the booleans/`Outcome` each method returns rather than inspecting flags directly.

`LiveConversationState` (`LiveConversationStateTest`) is the GPT-Live counterpart, same pure-Kotlin spirit but adapted to Live's different event shape: there is no turn-complete/speech-started-stopped/output-audio-done event, only `session.input_transcript.delta`/`session.output_transcript.delta` fragments that may arrive out of order, so `userSpeech`/`assistantSpeech` record a timestamp and `userSpeaking`/`assistantSpeaking` treat the speaker as still speaking for `SPEECH_HOLD_MS` (2s) after the last fragment (time is passed in as `now`, not read from the clock, keeping the class pure and testable); a delegated backend run is tracked via `delegationCreated`/`responseCreated`/`responseFinished` instead of one response lifecycle. Since there's no output-audio-done event to end the `end_conversation` farewell on, `readyToClose(now)` instead requires the flow to have been quiet — no follow-up/pending work, and `FAREWELL_QUIET_MS` (3s) since both `endRequested` and the last assistant transcript fragment — before `AssistantService`'s ticker sends `session.close` and starts a 3s fallback timer for `session.closed` never arriving. Because GPT-Live has no client-side event to cancel an in-flight response, `shouldNudge(now)` instead has `AssistantService` send a `session.instructions.append` nudge asking the model to stop and listen as soon as a user transcript fragment arrives while the assistant is still speaking, rate-limited to once per `NUDGE_INTERVAL_MS` (5s) and never while ending. `onLiveEvent` mirrors `onEvent`'s structure one level deeper, since GPT-Live nests Responses-API streaming events inside `response.event.event`: `response.output_item.done` (`function_call`) dispatches tools the same way Realtime's `response.function_call_arguments.done` does (factored into a shared `runToolAsync` helper, since the two only differ in the outer envelope — `conversation.item.create` vs. `response.item.create`), and `response.output_text.annotation.added` collects `url_citation` annotations (deduplicated by url) into a per-conversation `liveAnnotations` array, republishing `AssistantService.citations` as a single synthetic output_text-shaped part (one line of text per citation title, with matching `start_index`/`end_index`) so `MainActivity.showSources()` renders it unchanged despite Live having no tool-provided `content` array of its own.

`IdlePolicy(timeoutMs, shortTimeoutMs = timeoutMs)` is the other pure timing class (`IdlePolicyTest`): `update(now, busy)` (fed from the 250ms poll loop and from `input_audio_buffer.speech_started`/`response.created`, both of which count as busy) tracks when the conversation last went idle, and `expired(now)` says whether that's been at least `timeoutMs` ago — `settings.timeoutSeconds * 1000` normally. A device operation is a good moment to hang up quickly if the user doesn't say anything else, so `armShort()`/`disarmShort()` toggle a flag that makes `expired` use the much shorter `shortTimeoutMs` instead; `update` never touches this flag (the assistant's own follow-up speech after the tool result still marks busy via `response.created`, and that must not disarm it — only the user actually speaking, `input_audio_buffer.speech_started`, does). `AssistantService` constructs it as `IdlePolicy(settings.timeoutSeconds * 1000, POST_ACTION_IDLE_MS)` (`POST_ACTION_IDLE_MS = 5_000L`), calls `idle.armShort()` right after a tool result comes back on the worker thread — the same spot as the debug tool-call log — when the tool was `control_devices` with `"done": true` or `home_assistant` with `"type": "action_done"` (not for read-only tools like `get_device_states`/`list_home_devices`/`search`), and calls `idle.disarmShort()` alongside the existing `idle.update(..., true)` in the `input_audio_buffer.speech_started` handler.

- Web search: see "Search cards" below — `search_web` calls the Responses API with a strict JSON schema, returning a short spoken answer plus up to 5 picture cards shown on the home screen's standby viewer.
- Weather: the home display and conversation use the same weather-fetching layer. Region, coordinates, time zone, and fetch timestamp are managed, and the last fetch time is shown when offline. The provider is not yet selected.
- Remote MCP: a public HTTPS endpoint can be connected via Realtime MCP tools. The app handles authentication, allowed tools, approval events, and generating follow-up responses.
- LAN MCP: it is not assumed that OpenAI can reach the LAN directly. An extension path is planned where an Android-side MCP client connects and relays it as a function tool.
- stdio MCP: launching external commands on Android is out of scope initially. Only HTTP-based MCP connections are targeted.
- Home Assistant: implemented as a client-side function tool (`home_assistant`), following the same pattern as web search rather than Home Assistant's own MCP server integration, which would require exposing the LAN server publicly. `ToolClient.homeAssistant` sends the model's Japanese text straight to Home Assistant's Assist conversation API (`POST /api/conversation/process`, Bearer Long-Lived Access Token, `{"text": ..., "language": "ja"}`), and the pure function `parseAssist` reduces the response to a compact `{"speech", "type", "success", "failed"}` shape for the model. The tool is only added to the session's tool list when both the Home Assistant URL and token are configured. There is no per-call approval mechanism here (unlike the MCP tool's on-screen approval), so the model is instructed in its session instructions to confirm risky or high-cost actions (unlocking, anything costly or dangerous) verbally before invoking the tool, and, as with all tool results, to treat the returned `speech` as external data rather than new instructions. Assist's natural-language matching is unreliable both for state questions and for operating devices (unrecognized phrasing or device/room names produce a generic "didn't understand" response), so the tool's description and the session instructions now demote it to a *fallback*: state questions are routed to `get_device_states` and operations to `control_devices`, and `home_assistant` is called only when `control_devices` reports `unsupported_action` or the request can't be expressed as one of its fixed actions.
- Home Assistant device listing: a second client-side function tool, `list_home_devices` (`ListHomeDevicesTool`), gives the model (and the user, via Settings) visibility into which devices exist, their exact names, and their area, which `/api/conversation/process` alone cannot provide. `ToolClient.homeAssistantDevices` does `GET /api/states` (via `fetchStates`, below) and reduces the response through the pure function `parseStates` to `{"devices":[...],"count", "truncated"?}`, where each device is built with `deviceStateJson(entity)` (below) — so besides `name`/`id`/`type`/`state`/`area` it also carries `attributes`, keeping the Settings devices list and the model-facing tools on one shape. `name` falls back to `entity_id` when `friendly_name` is absent, `type` is the entity domain (text before the first `.`), `area` is `""` when Home Assistant has no area for the entity or areas could not be fetched, and the list is sorted by type then name. By default only domains a person would call an appliance (`DEVICE_DOMAINS`: light, switch, climate, fan, cover, lock, media_player, humidifier, vacuum, scene, script, input_boolean) are included, filtering out the long tail of sensors; an optional `domain` argument overrides this to list any single domain instead, and an invalid domain falls back to the defaults. The list is capped at `MAX_DEVICES` (150), sorted first, with a `truncated` flag when more matched. Registered alongside `home_assistant` under the same URL/token condition. The Settings → Integrations screen adds a "Home Assistant devices" row that calls the same `ToolClient.homeAssistantDevices` off the main thread and shows the result in a read-only scrollable dialog (`SettingsActivity.showDevicesDialog`), so the user can see what Butler sees (including entities not exposed to Assist, which `/api/states` lists but `home_assistant` cannot control) and can verify area lookup on-device. Devices are grouped into sections by area (areas sorted by name; devices with no area last, under a "No area" header in the accent gold used for the category highlight elsewhere in Settings), each rendered as a row of a rounded, outlined "kind" chip (localized via a domain → string map, e.g. `light` → "Light"/"照明"), the name and entity_id, and a state chip: filled gold with dark text when the pure function `isActiveState(type, state)` says the device reads as actively on/engaged, outlined and dim otherwise, or outlined in a muted red for `unavailable`/`unknown`. The state chip's label comes from the pure function `deviceStateKey(type, state)`, which maps the raw Home Assistant state string to one of a small fixed set of keys (`on`/`off`/`cool`/`heat`/`dry`/`fan_only`/`auto`/`heat_cool`/`open`/`closed`/`opening`/`closing`/`locked`/`unlocked`/`playing`/`paused`/`idle`/`standby`/`unavailable`/`unknown`, or `raw` — shown as the literal state text — for anything else) each with its own localized string (`on`/`off` split further into light-specific "点灯"/"消灯" vs. generic "オン"/"オフ" strings, since "on" reads oddly for a light in English/Japanese); a `climate` device's chip additionally appends its `current_temperature`/`temperature` attributes, when present, as "· now 24.5°C"/"· set 26°C" (numbers formatted without a trailing ".0").
- Area lookup: since `/api/states` carries no area/room field, `ToolClient.fetchAreas` fetches one separately with a Jinja template posted to Home Assistant's template API (`POST /api/template`, `{"template": "..."}`) that pairs every `entity_id` with `area_name(entity_id)` and returns them as one JSON array, parsed with a small `requestText` helper (same 1 MB size guard as the JSON helpers) since the endpoint replies with plain text rather than a JSON content type. The resulting `entity_id → area name` map is cached on the `ToolClient` instance for 10 minutes (`@Volatile` fields for the map and its timestamp) since areas rarely change and a request would otherwise be needed on every device lookup; any failure (HTTP error, timeout, malformed response) is caught and yields an empty map rather than surfacing an error, since areas are an enhancement to device matching, not a requirement — name-based matching keeps working without them. `ToolClient.fetchStates` (used by `homeAssistantDevices`, `homeAssistantDeviceStates` and `homeAssistantControl`) now calls `fetchAreas` and stamps a top-level `"area"` string field (`""` when unknown) onto every entity in the `/api/states` array before any pure function sees it, so `parseStates`, `resolveDevices` and `deviceStateJson` all read area the same way.
- Home Assistant device state: a third client-side function tool, `get_device_states` (`GetDeviceStatesTool`), answers "what's the state of X" questions — for one device or a whole group — by reading `/api/states` directly instead of going through Assist, so it no longer depends on Assist recognizing the phrasing, the device's name, or the room name. `ToolClient.homeAssistantDeviceStates(settings, target, domain)` fetches `/api/states` (via `fetchStates`) and reduces it with the pure function `resolveDevices(states, target, domain)`, returning its result as-is (already carrying state and attributes for every matched device).
- Multi-target device resolution: `resolveDevices(states, target, domain, area, forControl)` (replacing an earlier single-device `resolveDevice`) resolves a `target` string to *one or more* entities, since a phrase like "リビングの照明" ("the living room lights") should match every light in that area rather than forcing a single pick. An optional `area` argument pins the whole resolution to one room independent of `target`'s wording: if non-blank it is matched against known area names (equal, or an area name containing it, e.g. "リビング" matches the real Home Assistant area "リビングルーム") *before* anything else; no match returns `{"error":"unknown_area","areas":[...]}` (the distinct known area names, so the model can retry), a match restricts every subsequent step — including entity_id/exact-name matching — to that one room, and an empty (post-kind-extraction) `target` then resolves to every device (of the extracted kind, or every default-domain device when no kind was named) in that room. Otherwise the search space (`basePool`) is built the same way as before — entities in `DEVICE_DOMAINS` by default, a single domain when `domain` is a valid `[a-z_]+` string, or every entity when `target` contains a `.` (it looks like an entity id) — and resolution proceeds through a fixed precedence, stopping at the first step that produces a result: (1) an `entity_id` exactly equal to the trimmed target resolves to that one entity (`matched_by: "id"`); (2) a friendly name whose `normalizeDeviceName` output exactly equals the target's resolves to that one entity (`matched_by: "name"`) — this is how the model targets a single device deterministically, by reusing a full name or id from `list_home_devices`, regardless of what words the name happens to contain; (3) *kind extraction* — the longest `KIND_WORDS` key (a map of Japanese/English words like "照明"/"lights"/"エアコン"/"ac" to a domain) found in the normalized target is looked up and stripped out to leave a *residual*, along with any `ALL_WORDS` ("全部"/"all"/etc., tracked as `hasAllWord`); the kind's domain narrows the pool, but an explicit `domain` argument always wins as the domain used for narrowing, without skipping the word-stripping — so `target="リビングの照明", domain="light"` still isolates the residual down to "リビング" instead of leaving "照明" stuck in it; (4) if no `area` argument already pinned the room, a non-empty residual that equals or is contained by some entity's (normalized) `area` resolves every kind-matching entity in that area as a group (`matched_by: "area"`, plus an `"area"` field on the result) — if the area exists but holds no entity of the extracted kind, this returns `{"error":"not_found","area":..., "devices":[...]}` listing that kind's devices across the whole home instead; (5) if the residual is empty (the target was only a kind/"all" word, e.g. "照明" or "全部の照明"), every kind-matching entity resolves as a group (`matched_by: "kind"`) — or, if no kind was named either, `not_found`; (6) every kind-matching entity whose normalized name contains the residual resolves as a group (`matched_by: "name"`) — this is also the fallback when no area data is available at all; (7) otherwise the closest name(s) by the existing `deviceMatchScore` (threshold 0.3, `matched_by: "fuzzy"`), with ties within 0.05 of the top score reported back as `{"ambiguous": true, "candidates":[...]}` (up to 5, each including `area`) rather than guessed, and no match at all falling back to `not_found` with the default-domain device list. A resolved group's devices are ordered by type then name, and each is `{"name","id","type","state","area","attributes"}` via `deviceStateJson(entity)` (below), shared by `resolveDevices` and `ToolClient.homeAssistantControl` so both `get_device_states` and `control_devices` describe a device identically.
  - **Scope-widening guard (`forControl`)**: a real-world bug — "リビングの照明を消して" (turn off the living room lights) also turned off the bedroom light — traced to the model calling `control_devices` with `target="照明"` (a bare kind word, no room), which step (5) happily resolved to *every* light in the home. `get_device_states` still passes `forControl=false` (the read-friendly behavior above: a kind-only target returns every device of that kind), but `homeAssistantControl` now calls `resolveDevices(..., forControl=true)`, which tightens steps (5) and (6) so an operation can never silently widen beyond what the caller actually named: at step (5), with no `area` pinning the room and no `hasAllWord`, more than one kind-matching device returns `{"ambiguous": true, "candidates":[...≤5, with area], "reason": "kind_only"}` instead of the whole-home group — an "all"/"every" word (e.g. "全部の照明") or an `area` still returns the full group, since that's no longer an accidental widening but what the caller asked for. At step (6), a name-containment match spanning more than one distinct `area` with no `hasAllWord` is likewise returned as `{"ambiguous": true, "candidates":[...], "reason": "multiple_areas"}` rather than acted on. Neither guard fires when the match is inherently room-scoped already (an explicit `area` argument, or step (4)'s own area match), since that's not scope creep.
- Home Assistant device control: a fourth client-side function tool, `control_devices` (`ControlDevicesTool`), operates one or more devices directly by calling Home Assistant services instead of going through Assist, since Assist's matching is just as unreliable for operations, including room-scoped ones, as for state questions in this home. `ToolClient.homeAssistantControl(settings, target, action, value, domain, area)` first resolves the target with `resolveDevices(states, target, domain, area, forControl = true)` — the same resolver `get_device_states` uses, but with the scope-widening guard above turned on — returning its `ambiguous`/`not_found`/`unknown_area` result unchanged on a non-match, then, for every resolved device, looks up its *raw* (unfiltered) attributes from the already-fetched `/api/states` array and passes them, together with `action`/`value`, to the pure function `serviceFor(domain, action, value, attributes)`. `serviceFor` maps a small, fixed action vocabulary per entity domain (`DEVICE_ACTIONS`, e.g. `light`: turn_on/turn_off/toggle/set_brightness/set_color_temp; `climate`: turn_on/turn_off/set_temperature/set_hvac_mode/set_fan_mode/set_swing_mode; `cover`: open/close/stop/set_position; `lock`: lock/unlock; `media_player`: turn_on/turn_off/play/pause/stop/next/previous/set_volume/mute/unmute; `vacuum`: start/pause/stop/return_to_base; `scene`: activate; `script`: run; plus `switch`/`input_boolean`/`fan`(+set_speed)/`humidifier`(+set_humidity) turn_on/turn_off/toggle) to a `ServiceCall(domain, service, data)` — e.g. `set_brightness` "50" becomes `light/turn_on {brightness_pct: 50}`, `set_volume` "40" becomes `media_player/volume_set {volume_level: 0.4}`. Percent-style values are parsed and range-checked to 0..100, `set_temperature` takes a bare number, and `set_hvac_mode` accepts English or Japanese synonyms ("冷房" → `cool`, etc.) normalized to Home Assistant's ids; `set_hvac_mode`/`set_fan_mode`/`set_swing_mode` are additionally validated against the entity's `hvac_modes`/`fan_modes`/`swing_modes` attribute arrays when Home Assistant reports them, and rejected (returning `null`) otherwise. A device whose `serviceFor` call returns `null` is put into a `skipped` list instead of failing the whole request — `{"name","type","reason":"invalid_value"|"unsupported_action","supported":[...]?}` — `invalid_value` when `action` is one `DEVICE_ACTIONS[domain]` recognizes (bad/missing/out-of-range `value`), `unsupported_action` (with the domain's `supported` list) when it isn't; if *every* resolved device is skipped this way, the call returns `{"error": <the skip reason, or "unsupported_action" when reasons differ>, "skipped":[...]}` so the model can fix the value or fall back to `home_assistant`. The remaining (device id, `ServiceCall`) pairs are combined by the pure function `groupServiceCalls`, which groups entries sharing the same domain+service+data into one `GroupedServiceCall(domain, service, data, entityIds)` each (e.g. turning off two living-room lights becomes one `light/turn_off` call with both entity ids) — this keeps a room-wide command to a small, fixed number of Home Assistant requests regardless of how many devices matched. The tool `POST`s `${haUrl}/api/services/<domain>/<service>` once per group with the service data plus an `"entity_id"` array, then re-`fetchStates`s once and returns `{"done": true, "action", "matched_by", "area"?, "devices": [<deviceStateJson(...)> for every targeted device, in resolution order], "skipped"?}` (`skipped` omitted when empty). Registered alongside the other three tools under the same URL/token condition; the session instructions and all four tools' descriptions steer the model to call `control_devices` to operate devices — passing the user's own wording as `target` and the named room, if any, separately as `area` — never widen scope beyond what the user said (ask, or pass `area`/an "all" word, when the result is `ambiguous`) and report results plainly (no "operating several devices" preamble; state the device or the count) — `get_device_states` for any state question, `home_assistant` only as a fallback when `control_devices` can't express the request, and `list_home_devices` when asked what devices exist, when a name or area is unclear, or when a tool fails to find a match — reusing the exact `name`/`area`/`id` it returns. `ToolClient.homeAssistantCallService(settings, entityId, action, value, attributes)` and `homeAssistantImage(settings, path)` are a separate, simpler direct-entity-id path (no resolution, `serviceFor` reused as-is) used by the on-screen smart-home and music pages, which already know exactly which entity they're operating.
- Tool-call debug logging: since a misbehaving tool call (like the scope-widening bug above) is otherwise invisible without instrumenting the model's own reasoning, `AssistantService`'s `response.function_call_arguments.done` handler now logs, only in debug builds (`if (BuildConfig.DEBUG)`), each tool invocation as `Log.i("Butler", "tool <name> args=<arguments> -> <result, truncated to 400 chars>")` right after `tool.execute(...)` returns (or fails) — visible via `adb logcat -s Butler` on a debug build, without touching the release build or the response sent back to the model.

Read operations are distinguished from operations that make external changes, and the content of change operations is shown on screen for confirmation. Tool results are treated as external data, and instructions embedded within a result must not override settings or permissions. Limits are placed on call count, response size, and execution time.

### Search cards

`search_web` (`SearchWebTool`) answers with a short spoken reply *and* up to `SearchCards.MAX_ITEMS` (5) picture cards, shown on the home screen's standby viewer (`SearchCardsView`, below) and readable aloud on tap. `ToolClient.searchCards(settings, input)` calls the Responses API the same way `search` always did (`tools:[{"type":"web_search"}]`, `tool_choice:"required"`) but with a strict `text.format` json_schema (`{spoken: string, items: [{title, description, url, wikipedia_title: string|null, image_query}] (maxItems 5)}` — `additionalProperties:false` and every property `required` are both mandatory for `strict:true`, and the nullable `wikipedia_title` is expressed as `"type":["string","null"]` rather than making it optional; confirmed against the live API), returning the raw `output_text` JSON string. `SearchCards.parse` (pure, unit-tested in `SearchCardsTest`) decodes that into `{spoken, items}` — tolerant of missing/blank fields (an item missing `title`/`url` is dropped, `items` beyond 5 are ignored, each `description` truncated to ~300 chars) but *not* of the root not being JSON at all, which throws; `SearchWebTool.execute` catches only that case and falls back to the old text-only `ToolClient.search`, so a card-search regression can never make search itself worse than before. A call failure (HTTP error, timeout) is not caught here — it propagates to `AssistantService.runToolAsync`'s existing `{"error":...}` handling, same as any other tool.

Image resolution (`SearchWebTool.resolveCardImages`) runs on the worker thread in two parallel phases, each with its own ~5s budget: an `ExecutorService.invokeAll(tasks, 5000, MILLISECONDS)` over 4 threads (one task per item) cancels whatever hasn't finished when the budget expires, so one slow/unreachable image host can't make search itself slow; each pool is created and torn down within the call rather than kept as a field, since `SearchWebTool` is recreated every conversation (`ToolRegistry(this, settings, client)` in `AssistantService.begin()`). Phase 1 resolves a picture *URL* per item (no download yet, `resolveImageUrl`), in order: (1) Google Programmable Search's image API (`ToolClient.googleImageSearch`, `searchType=image&num=1&safe=active`) using the model's `image_query`, only when both `Settings.secret("googleCseKey")` and `Settings.get("googleCseCx")` are set (Settings → Conversation, both optional — without them cards fall back to Wikipedia pictures only; 100 free queries/day); (2) failing that, `ToolClient.wikipediaThumbnail(wikipedia_title, lang)` — the `ja`/`en` REST summary endpoint's `thumbnail.source` (a real subject photo, unlike a page's `og:image`, which is usually a site-wide logo and isn't used at all), falling back to the tolerant search-by-title endpoint when the exact title 404s, both sent with a descriptive `User-Agent` per Wikimedia's API etiquette; (3) otherwise no URL — a text-only card. **No duplicate pictures**: the model often returns several items about the same subject (e.g. four capybara facts), all naming the same `wikipedia_title`, which would otherwise all resolve to the identical Wikipedia thumbnail; before any download happens, a repeated `wikipedia_title` is only kept for its first item (later ones lose their URL even if the resolved string happens to differ, e.g. a redirect — Wikipedia-tier resolutions only, since two items legitimately sharing the same Google image result are a separate case), and then `SearchCards.dedupePictureUrls` (pure, unit-tested in `SearchCardsTest`) keeps a URL only for its first exact-string occurrence across all items, nulling out any later repeat regardless of tier. Phase 2 downloads/decodes only the URLs that survived dedupe (`downloadImage`): fetched (`ToolClient.fetchImageBytes`, capped at 3MB, 4s per-request timeout) and downsampled with `inSampleSize` to ≤960px on the long side — matching the 960px-wide device display so a full-screen card picture isn't visibly soft — (same approach as `MusicPage.decodeSampled`, duplicated locally since the two live in different packages). An item that loses its picture at any step — no tier resolved a URL, dedupe removed it, or the download/decode failed/timed out — becomes a text-only card (`SearchCards.Card.bitmap == null`).

`SearchCards` (`SearchCards.kt`) is the process-wide holder `search_web` publishes into — `data class Card(id, title, description, url, bitmap: Bitmap?)`, `var query`, `var cards: List<Card>`, `var serial: Int` — the same static-state pattern as `AssistantService.status`/`homeStateSerial`, but with `@Volatile` fields swapped in as whole immutable lists (`publish`/`clear`, both `@Synchronized`) rather than main-thread-only writes, since `SearchWebTool.execute` runs on `AssistantService`'s worker thread, not main. The tool result sent back to the model is `{"answer": spoken, "cards": [{"number","title","description","source","picture": true|false}], "shown_on_display": true|false, "content": [...]}` — `content` is `SearchCards.buildContent(items)`, one `output_text` part whose `text` lists each item's title on its own line with a `url_citation` annotation per line (`start_index`/`end_index` covering that line), the same shape `AssistantService` (`citations = result.optJSONArray("content")`) and `MainActivity.showSources()` already understand, so the Sources dialog keeps working unchanged even though the strict-schema Responses call itself returns no `url_citation` annotations on its own `output_text` part (verified live — the model's `spoken` text carries no citation markup either).

Both voice APIs now call `search_web` as a client-side function tool: Live used to swap it out for the hosted `web_search` tool type in `ToolRegistry.liveDefinitions()`, but that hosted tool can't return picture cards, so Live now calls the same `search_web` function Realtime does, and its result's `content` array feeds `AssistantService.citations` from the ordinary function_call_output path in `onLiveFunctionCall` (mirroring `onEvent`'s Realtime handling) — `addLiveCitation`/`response.output_text.annotation.added` is kept since the delegation backend can still cite pages on its own, but a hosted `web_search` call itself no longer happens. The session instructions (`prompt_realtime_instructions`/`prompt_live_instructions`/`prompt_live_backend_instructions`) tell the model that search results are shown as numbered picture cards, to say the answer and then briefly read the cards aloud in order unless the user asked a narrow factual question, and that the user may ask for one card in detail by number or name.

**`SearchCardsView`** (`SearchCardsView.kt`) is a `FrameLayout` MainActivity adds to its root above the pager and below `ConversationView` (landscape 960x480, following the `WeatherPage`/`MusicPage` glass-card look via `Ui.kt`'s `dp()`/`glassCard`/`roundedShape`/text helpers) — it reserves a 70dp top margin for `ConversationView`'s own docked bar (drawn on top of it, not by it) rather than rendering one of its own. MainActivity's 250ms tick compares `SearchCards.serial` to a tracked value, next to its `homeStateSerial` check: a new serial with non-empty `SearchCards.cards` calls `SearchCardsView.show(query, cards)` (fades in, docks the conversation overlay exactly like the weather auto-switch, resets `lastTouchAt`), a new serial with empty cards calls `hide()` instead (that only happens via `SearchCards.clear()`: a search whose `items` came back empty — a plain fact, a number — does not publish at all, so the previous cards stay on the standby viewer). The default mode is a header line (the query, small cream 60%, tight margins so the strip below gets most of the height) above a `HorizontalScrollView`/`LinearLayout` card strip that stretches nearly to the bottom edge (10dp margin): each card is `(strip width − 14dp gap) / 2` wide — two cards per screen, recomputed from the view's own measured width in `onSizeChanged` (352dp before the first layout pass) — and full height. A card with a picture (`pictureCardView`) fills the whole card with it (`CENTER_CROP`, rounded 18dp corners, clipped via `clipToOutline`), with the number+title (one line), a 2-line ellipsized description and the source domain overlaid on the picture's lower part on a vertical gradient scrim (transparent → ~85% dark); a card without one (`textOnlyCardView`, `SearchCards.Card.bitmap == null`) is the same size instead of an empty picture tile — a translucent "glass" fill (`Palette.CREAM_12` + a faint stroke), the number+title (16sp, up to 2 lines) at the top, then as much of the description (13sp) as the card's actual height allows — computed once from a post-layout `View.OnLayoutChangeListener`, since the strip only tracks card width up front, not height — and the source domain pinned to the bottom via a weighted spacer. Both card kinds end with the same highlight-border overlay as their last child, so `tick` (below) treats them alike. Tapping a card switches to a full-screen mode (`showFullScreen`/`showList`) covering the whole view, split so a picture and its text never overlap: `fullSplitRow`, a horizontal row of `fullPictureHolder` (the bitmap `FIT_CENTER` on a near-black ~92%-opaque backdrop) and `fullRightColumn` (back arrow, number+title 20sp, the description 14sp in a `ScrollView` that scrolls instead of truncating, the source domain, and a "Read aloud" button). With a picture, `fullPictureHolder` is the left half and `fullRightColumn` the right half, snug against it; without one, `fullPictureHolder` is set `GONE` (dropping its width claim in the `LinearLayout`, so `fullRightColumn`'s own weight fills the whole row on its own) and `fullRightColumn` gets wider side margins instead — one column reused for both cases via `applyRightColumnLayout`, rather than two separate layouts. `fullRightColumn` always carries a ~70dp top margin so its title clears the docked-conversation-bar zone and stays readable while a conversation is docked. "Read aloud" is hidden when `settings.voiceApi == VoiceApi.LIVE`, since `AssistantService.say` doesn't support Live. Tapping the picture itself, or the back arrow, returns to the strip. A small × button (top-right) calls `hide()` directly, staying on top and clickable in both modes. The currently-relevant card gets a brighter (gold) border: `tick(transcript)`, called every MainActivity tick, does a cheap `SearchCards.highlightMatches` substring check (the card title, or its first 8 characters, appearing in `AssistantService.transcript`) and only touches a view when the matched card id actually changed. The viewer persists after the conversation ends (it *is* the standby viewer) until `hide()` — the × button, a new search with cards of its own, or MainActivity's pager auto-return timer (`AUTO_RETURN_MS`/`lastTouchAt`, the same timer and window the pager itself uses, but never while a conversation is active); `pager.locked` includes `SearchCardsView.standbyShown` for as long as it's up, and hiding it also calls `SearchCards.clear()` to drop the (at most 5, ≤640px) bitmaps.

`AssistantService.say(text)` (main thread) has the model read `text` verbatim through an out-of-band `response.create` (`conversation: "none"`, per-response `instructions` from `prompt_read_aloud`) — not a user turn: the first version injected the text as a user message and the model answered it instead of reading it — used by `SearchCardsView`'s "Read aloud" button, via `MainActivity.action(AssistantService.SAY, text)` → `AssistantService.SAY`/`EXTRA_TEXT` → `onStartCommand`. If a conversation is active and ready, it sends a `response.cancel` first when `state.responding` (so the read-aloud reply doesn't talk over/queue behind an in-flight response) then the usual `conversation.item.create` (`input_text`) + `response.create` pair (factored into `sendUserText`, also reused by the existing `debug.butler.say` hook, `checkDebugSay`); if no conversation is active, it calls `begin()` and queues the text in `pendingSay`, injected once `session.updated` reports the session ready (no wake chime, since this isn't a wake-triggered conversation — `chimeOnReady` stays false). Realtime only: GPT-Live has no verified client event for injecting a text user turn (same limitation `debug.butler.say` has always had for Live), so `say()` just logs a warning there, and `SearchCardsView` hides its "Read aloud" button on Live for the same reason.

**Settings**: two new optional rows under Settings → Conversation, "Image search API key (Google)" (`Settings.secret("googleCseKey")`) and "Image search engine ID" (`Settings.get("googleCseCx")`), each with a helper line noting that without them cards fall back to Wikipedia pictures only.

**Debug hook**: `adb shell setprop debug.butler.cards 1` (debug builds only, read in MainActivity's tick like `debug.butler.talk`) loads four fake cards — three with placeholder bitmaps drawn in code plus one text-only card (`bitmap = null`) — via `SearchCards.debugCards()`/`SearchCards.publish`, so both the strip's and the full-screen mode's picture and text-only layouts can be checked on-device without a real search; `0`/blank clears them again (`SearchCards.clear()`), but only when this hook was the one that showed them, so a production build's always-blank property can never clear a real search's cards.

## Home screen and settings

The home screen is a swipeable four-page `PagerView` (`app/src/main/java/dev/syumai/butler/PagerView.kt`, a small from-scratch reimplementation of the slice of `ViewPager` this app needs — no AndroidX anywhere): ClockPage (the big clock/date, a weather mini text top-left that jumps to WeatherPage on tap, and a status line shown only for attention-worthy states such as a missing API key or a connection failure — not the routine idle/listening/responding flow), WeatherPage (today's and tomorrow's forecast as two glass cards — condition, high/low with the change vs. yesterday, and a 6-hour precipitation table — or an empty state when the region isn't configured or nothing could be fetched), SmartHomePage (a live grid of Home Assistant devices with a bottom-sheet control panel), and MusicPage (Home Assistant `media_player` control). A floating tab strip (top-left, fading in on any page but the clock) and a row of page dots (bottom-center, always visible) sit above the pager; the settings gear stays fixed top-right on every page, as before. Any touch resets a 3-minute idle timer; once it lapses while on a page other than the clock and no conversation is in progress, the pager animates back to page 0 on its own.

During a voice conversation, a full-screen `ConversationView` overlay (`ConversationView.kt`) replaces the old always-present Talk/End/Sources button row: an animated `OrbView` blob (teal while listening/connecting, brass while speaking, a faster pulse while a tool runs), a status line, a "you"/assistant caption pulled from live transcripts — each line bounded to its own small `ScrollView` (2 lines for "you", 4 for the assistant, capped from the TextView's own line height so it grows with short text and scrolls once longer) that auto-scrolls to the newest words on every update unless the user dragged it in the last ~5s — an end button, a Sources button (shown once the conversation has citations), and an approval pill (shown while an MCP call awaits on-screen confirmation) — all driven by one cheap `ConversationView.update(...)` call from `MainActivity.tick` that only touches a child view when its value actually changed. It shows and hides with a 300ms fade tied to `AssistantService.conversing`, and locks the pager (and the device sheet, while open) against swipes for as long as it's up. User speech is now transcribed live too, not just the assistant's replies: the Realtime API is asked for input transcription via `session.audio.input.transcription.model = "gpt-live-transcribe"` (streamed as `conversation.item.input_audio_transcription.delta`/`.completed` events), while GPT-Live already streams the user's side natively as `session.input_transcript.delta` — both feed `AssistantService.userTranscript`, shown as the caption's "you" line. When the model calls `get_home_weather` mid-conversation, the pager auto-switches to WeatherPage and the conversation overlay animates into a small docked mode (the orb shrinks into the top-left corner, the caption becomes a translucent bar along the top edge, where the tab strip normally sits) so the user can see the forecast and keep talking at once; SmartHomePage and MusicPage refresh the same way whenever a device operation completes, all keyed off small serial counters (`AssistantService.viewRequestSerial`, `.homeStateSerial`) that `MainActivity.tick` compares each tick rather than polling state directly. Since the overlay can't otherwise be exercised without a live conversation, a debug-only override (`BuildConfig.DEBUG` gated, alongside `debug.butler.scene`/`.minute` below) lets `adb shell setprop debug.butler.talk 1` drive it with a fake exchange (a `status_responding` status, a canned "you"/assistant transcript, no citations) — full-screen mode; `2` does the same but docked, also switching the pager to WeatherPage like the real auto-switch above, so both layouts can be screenshotted on-device.

A separate debug-only hook lets a real conversation turn be driven from adb without a microphone: `adb shell setprop debug.butler.say "今日の天気は？"` while a conversation is active injects that text as the user's turn (Realtime only — GPT-Live has no verified client event for injecting a text user turn, so this just logs a warning there); release builds ignore the property. Since the redesign removed the old on-screen Talk button (and the service isn't exported, so `am start-foreground-service` from the shell is denied), `adb shell setprop debug.butler.begin 1` starts a conversation exactly as the former Talk button did; set it back to 0 before reusing the same value again; release builds ignore it too.

Background rendering has three levels of precedence: the weather scene (when the "weather-linked background" setting is on and the current scene is known) takes priority over the imported photo, which in turn takes priority over the original code-drawn sky illustration (no ground/ridge geometry — see below). `WeatherScene` maps the same Open-Meteo weather code and day/night flag already used for the weather text into a coarse scene (clear/partly cloudy/cloudy/fog/rain/snow/thunder), and it is recomputed on each periodic weather refresh. `Landscape` (the background `View`) and its private `SceneArt` helper live in `app/src/main/java/dev/syumai/butler/Landscape.kt`, moved out of `MainActivity.kt`; `MainActivity` still just constructs `Landscape(this, settings.background, settings)` and sets `.scene`. `SceneArt` holds the deterministic base geometry for one scene at one view size (seeded by the scene, so re-creating it always lays out the same stars/clouds/rain), pairing a vertical sky gradient and a sun/moon disc with a soft radial glow behind it, plus simple elements (stars, clouds, rain streaks, snow, lightning).

Weather scenes now animate (clear-day stays static): rain and snow fall, clouds and fog drift, night stars twinkle, and thunder flashes periodically. The loop runs only while the view is attached, its window is visible, and the current scene has motion — `postInvalidateDelayed(40)` from `onDraw` caps it at ~25 fps, timed off `SystemClock.uptimeMillis()` so motion stays smooth regardless of how often frames are actually drawn. To keep this cheap on the target device (960x480, 32-bit ARM, weak CPU), `SceneArt` bakes the parts that never move — the sky gradient, the sun/moon glow, and the sun/moon disc itself — into a `Bitmap` once per scene/size instead of redrawing them every frame; `Landscape.onDraw` just blits that bitmap and then draws only the moving elements (rain/snow buffers mutated in place, cloud drift and star twinkle computed straight from elapsed time) with no per-frame allocation. Rain (used by both RAIN and THUNDER) is drawn in three depth layers — far streaks short/thin/dim/slow, near streaks long/thick/bright/fast — all sharing one `RAIN_SLANT` dx/dy ratio for both a streak's own tilt and its fall direction, so it reads as nearly vertical rain with a slight, consistent wind lean rather than an arbitrary angle. On-device measurement with `top -H` while RAIN was showing found the actual render cost (RenderThread + main/UI thread) at roughly 8-11% of one core, with the process-level total looking much higher.

A debug-only override (`BuildConfig.DEBUG` gated) lets `adb shell setprop debug.butler.scene <SCENE>` force a specific scene — and force the weather background on — for on-device checks without needing matching live weather.

The sky is a vertical gradient (top → horizon, `LinearGradient(0,0,0,h,...)`) topped with a small sun/moon disc and a soft radial glow behind it (`drawGlow`, shared by the default illustration and `SceneArt`'s baked bitmap); there is no ground or ridge geometry — the background is sky only. The default illustration's colors (sky gradient stops and sun color; disc position/radius, gradient direction and paint/AA settings are unchanged) follow the time of day: night → dawn → morning → noon → evening → night, interpolating smoothly rather than jumping between scenes. `DayPalette` (`app/src/main/java/dev/syumai/butler/DayPalette.kt`) is pure Kotlin with no `android.*` imports, so it is unit-tested on the JVM (`DayPaletteTest.kt`): a small list of (minute-of-day, palette) keyframes — anchored to the `CLEAR_NIGHT` and `CLEAR_DAY` scene colors above at midnight/noon, and to the original hard-coded illustration colors at 18:00 as the evening keyframe, so the existing sunset look is preserved — with `DayPalette.at(minuteOfDay)` linearly interpolating each ARGB channel between the two neighbouring keyframes, wrapping across midnight. `MainActivity`'s `tick` runnable (every 250ms while visible) converts the current time into a minute-of-day and assigns it to `Landscape.minuteOfDay`; the setter only calls `invalidate()` when the minute actually changes, so this costs nothing beyond one comparison on most ticks. A debug-only override alongside `debug.butler.scene` — `adb shell setprop debug.butler.minute <0..1439>` — forces the minute used for the palette, read each tick via a cheap `SystemProperties.get` call.

Configurable items:

- OpenAI API key, voice API (Realtime or GPT-Live), voice model (per api: `model`/`liveModel`), voice (per api, `Voice.forApi`), and the search/backend model (also the GPT-Live delegation model).
- Number of seconds of silence before ending the conversation. 30 seconds is a provisional default, not a confirmed user value.
- Weather region search/selection, with direct latitude/longitude entry as an option.
- Background image, 12/24-hour clock display, and the weather-linked background toggle.
- Wake detection is on-device, engine selectable (Julius default, Vosk the selectable alternative) with no other tunable parameters; the standby toggle and engine choice are exposed in Settings.
- MCP server URL, authentication, tools to use, and approval policy.
- Home Assistant server URL and access token, with a one-tap connectivity check.
- Starting/stopping microphone standby.

Settings and the weather cache may be persisted, but recordings and conversation history are not saved. Not saving in-app history is a separate matter from the API provider's own data retention.

Settings live in a dedicated `SettingsActivity` (started from the home screen's settings button) rather than a dialog, laid out as a two-pane, Android-Settings-style screen sized for the landscape 480px-tall device: a fixed-width category list on the left and a scrollable row list on the right. Categories: Conversation (OpenAI API key, voice API selection, voice/search-backend model, assistant voice, silence timeout), Wake (standby toggle, the fixed wake phrase display, wake engine selection — no threshold to configure), Weather & background (region, latitude/longitude, weather-linked background toggle, background image picker/reset), Integrations (Home Assistant URL/token and connectivity check, MCP server URL and bearer token), and About (app name/version, third-party notices). Every row change is saved immediately (no global save button); text/number rows open a compact single-EditText dialog, switches toggle inline. Entering the screen stops the assistant service, and a change in a category that affects it (Conversation/Wake/Integrations) restarts or stops it right away — the same start-if-enabled/stop-otherwise behavior the old dialog applied on save. Background/weather changes set an in-memory `Settings.dirty` flag that `MainActivity` checks in `onResume` to rebuild the home screen. A voice change takes effect from the next conversation only, since both APIs lock the voice for a session once it has produced its first audio response. The "Voice API" row is a single-choice dialog (Realtime/GPT-Live); switching it changes which model key the "Voice model" row edits (`model` vs. `liveModel`) and which voices the "Assistant voice" row's picker offers (`Voice.forApi(settings.voiceApi)`, via `settings.voice(api)` which falls back to that api's default — `marin`, valid for both — when the stored voice isn't valid for the newly selected api); the "Search / backend model" row (`searchModel`) is shared — it's both the Realtime-side web-search model and, for GPT-Live, the delegation backend model that does reasoning/tool selection while the voice model paraphrases its results.

### Smart home and music pages

Two of the home screen's pager pages (see the pager/tabs/dots structure introduced alongside them) are driven by Home Assistant: `SmartHomePage` (`app/src/main/java/dev/syumai/butler/SmartHomePage.kt`) and `MusicPage` (`MusicPage.kt`). Both are plain `FrameLayout`s with the same small lifecycle contract — `onShown()`/`onHidden()`/`refresh()` — that `MainActivity` drives off the pager's current page and off `AssistantService.homeStateSerial` (so the grid/now-playing view updates itself right after the assistant operates a device by voice, not just on the next poll). Each page fetches `ToolClient.homeAssistantDevices` on its own single-thread `ExecutorService` worker, posts results back to the main thread via a `Handler`, and drops results from a stale/superseded fetch (tracked with a generation counter) or from after the page was hidden. `HomeStore` (`HomeStore.kt`) is a small shared, in-memory cache of the last-fetched device list plus a serial number, so switching between the two pages shows the previous page's freshly-fetched list immediately instead of a blank page while its own fetch is in flight; `SmartHomePage` polls every 30s while shown, `MusicPage` every 10s.

`SmartHomePage` renders every device (`light`, `switch`, `climate`, `fan`, `cover`, `lock`, `media_player`, `humidifier`, `vacuum`, `scene`, `script`, `input_boolean`) as a tile in a 4-column scrolling grid, sorted by area then a fixed device-kind order then name, with a compact per-domain state line (`DeviceText.tileStateLine`) distinct from the longer label `SettingsActivity`'s devices dialog uses (`DeviceText.stateLabel`) — both now live in `DeviceText.kt`, moved out of `SettingsActivity` so the tile grid, the sheet, and the settings dialog describe a device the same way. Tapping a tile opens `DeviceSheet` (`DeviceSheet.kt`), a bottom sheet that slides up over the grid and locks the pager (`SmartHomePage.onSheetOpenChanged` → `MainActivity` sets `pager.locked`) while it's open; a scrim tap or its close button dismisses it. The sheet's body is built per Home Assistant domain, from a plain toggle (switch/input_boolean) up to the climate control's `DialView` (`DialView.kt`, a custom `View` drawing a 270° arc track/progress with the target temperature centered) with mode/fan/swing chips, and the light control's brightness/color-temperature sliders and preset scene chips. Every control action calls `ToolClient.homeAssistantCallService(settings, entityId, action, value, attributes)` directly on the worker (no natural-language resolution, since the sheet already knows the exact entity) and, on success, asks the owning page to refresh after an 800ms delay so the UI reflects Home Assistant's actual resulting state rather than only the optimistic local guess; a failure shows a `Toast`. Climate's +/- stepper debounces `set_temperature` calls by 600ms so repeated taps don't spam the API.

`MusicPage` is a best-effort now-playing view over whichever `media_player` entities Home Assistant exposes — there is no direct Spotify SDK or Android notification-listener integration, so playback the phone/TV is doing outside of a `media_player` entity Home Assistant knows about won't show up here. It picks the first playing player, else the first paused one, else the first found (with chips to switch manually when there's more than one), shows artwork fetched via `ToolClient.homeAssistantImage` and decoded with `inSampleSize` capped to 512px (cached in memory by URL), and computes a live progress bar from `media_position`/`media_position_updated_at` (an ISO-8601 timestamp with an offset, parsed via `java.time.OffsetDateTime`, tolerant of any number of fractional-second digits) plus elapsed wall-clock time while playing, ticking once a second without any extra network traffic. Transport/volume/mute controls go through the same `homeAssistantCallService` call used by the device sheet.

### Localization

The UI and the model-facing conversation follow the OS locale rather than being fixed to Japanese: English is the default, and Japanese is used when the device language is Japanese. Every user-facing string lives in `app/src/main/res/values/strings.xml` (English) and `app/src/main/res/values-ja/strings.xml` (Japanese), resolved by Android's normal resource system, so `MainActivity` and `SettingsActivity` render entirely from resources with no hardcoded language. Because `AssistantService`'s status line is held as static state on a background service rather than rendered directly, it is stored as a small `Status(textResId, vararg args)` wrapper (`Status.kt`) instead of a resolved `String`, and only turned into text via `Status.resolve(context)` at display time in `MainActivity.tick` — this keeps the status correct even if the OS locale changes while the service is alive. The same principle extends to the model: `RealtimeSignaling`/`LiveSignaling`'s session `instructions` (`prompt_realtime_instructions`, or `prompt_live_instructions`/`prompt_live_backend_instructions` for GPT-Live's voice/backend split), the tool descriptions in `ToolRegistry`/`SearchWebTool`/`HomeAssistantTool`, and the `search_web`/`home_assistant` prompt text are all built with `context.getString(...)`, so the assistant is instructed to converse in, and the web-search tool answers in, the current UI language. `HomeAssistantTool` additionally passes `java.util.Locale.getDefault().language` through to Home Assistant's Assist API instead of a hardcoded `"ja"`, so appliance responses follow the same locale.
